# Upstream maintenance

`origin` is the writable zhavir/ultimate-u1-slicer project; `orca-upstream` tracks official OrcaSlicer; `snapmaker`, `forca`, `snapmaker-profiles` and `extended-firmware` point to the verified public sources. SnOrca is an alias of `snapmaker`, not a second remote with independent changes. Official MCP is tracked through orca-upstream/feature/mcp. Exact audit baselines live in tools/u1/sources.lock.json and must not move implicitly during a build.

Run `python3 tools/u1/upstream_review.py --fetch --probe-merges` to fetch source branches and generate a review report. Without `--fetch`, unavailable refs are reported as unavailable. The tool classifies changed paths, records commits and flags paths that overlap local patches. A path overlap is a potential conflict, not a proof that a merge conflicts. The optional merge-tree probe checks textual merges for changed official Orca/MCP branches without changing HEAD, the index or source files. It does not test semantic compatibility. Full merges of the other repositories are not probed because this architecture requires scoped adapters/cherry-picks instead. A non-overlap does not prove API or behavioral compatibility. Commit lists are unfiltered candidates, not reviewed recommendations.

The six-hour `u1-upstream-review.yml` workflow now runs `tools/u1/upstream_watch.py`. It observes the nine configured source branches plus 30 recent releases/tags per repository, including prereleases, release edits and retargeted tags. Fixes/features are detected as branch commit changes; their implementation still requires inspection. Each new event opens an `upstream-update` issue assigned to the maintainer in `.github/u1-maintenance.json`. Fingerprints in all open/closed labeled issues suppress repeats. Releases/tags are deduplicated across official main/MCP aliases; a same-run release covers its corresponding tag. No third-party code is executed, no source is merged and no branches/PRs are created by the notification workflow.

`.github/u1-upstream-baseline.json` records initial release/tag observations. Branch drift is compared against reviewed source pins, so the first run also reports already-known unintegrated changes. Refreshing the notification baseline does not advance integration pins. API/ref failures are reported explicitly as monitor-error events without hiding independent sources. Up to 25 issues are created per run; remaining events are retried later and the run reports the cap. Closing an issue does not re-create the same event. This is polling: short-lived changes between polls and historical items outside the recent window are not guaranteed to be captured.

The project maintenance procedure is `.claude/skills/ultimate-u1-maintenance/SKILL.md`, linked by root AGENTS.md. Use the exact source compare links from an issue, run the separate source review tool, test selected integrations and update evidence before pushing the authorized project main branch. Never push to source repositories.

Actual integration must use a separate integration branch based on a known passing release or integration checkpoint. Review relevant changes by engine/schema/G-code, MCP, connectivity, profiles, dependencies, UI and CI. Prefer isolated cherry-picks; keep upstream commit attribution, resolve semantic conflicts explicitly and add compatibility adapters where schemas differ. Update source pins only after the affected features pass their relevant tests. Never resolve a merge by deleting a U1 feature.

Required gates depend on subsystem: native protocol/core tests for MCP; compiled profile loader and inheritance/array checks for presets; actual model-to-G-code comparisons for slicing; captured-response and permission tests for networking; all platform builds after dependency changes. Existing U1 3MF projects and configuration migrations are mandatory release tests. Hardware tests stay manual and separately authorized.

At present there is no Ultimate U1 known-good stable release. Keep the audited published Snapmaker release as an external reference and do not label the experimental branch stable. Once a release passes all offline gates, preserve it with an immutable tag/artifact/checksum and keep integration ahead of that tag. Physical compatibility remains provisional until the separate hardware checklist passes.

The initial workflow provides change detection and review automation only. Automatic source integration, full compatibility gating and release artifact retention are not complete until their application-level tests and runners are available.
